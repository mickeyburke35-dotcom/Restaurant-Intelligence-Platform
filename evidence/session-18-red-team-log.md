# Session 18 Red-Team Log

Devil's Advocate review for the Restaurant Intelligence Platform. This challenges the concept honestly and marks pending work or accepted risk where the current repo does not prove implementation.

| Objection | Severity | Response | Change made / Decision |
| --- | --- | --- | --- |
| Business problem: agencies may already manage reviews inside existing platform dashboards or spreadsheets, so the pain may not be urgent enough to buy another tool. | High | The product must prove value through cross-client workflow, evidence-linked insights, report generation, and reduced manual review synthesis. No market demand or traction is claimed. | Accepted risk. Future validation should interview agency owners, account managers, and consultants before expanding scope. |
| User need: Manager, Analyst, and Viewer/Client roles may hide different needs, and the current docs may over-compress their workflows. | Medium | The role model is a reasonable v1 starting point, but onboarding and permissions need real user testing. Viewer/Client read-only behavior remains important. | Pending. Keep roles from PRD for v1, then validate task flows with representative users. |
| Architecture: one Next.js app with API routes and jobs in the same repo is clear for v1, but scheduled jobs, exports, and large imports may outgrow route-handler limits. | Medium | The architecture already allows Render or Railway for jobs and backend services that do not fit Vercel runtime limits. | Decision: keep current architecture for v1. Revisit service boundaries only when imports, exports, or schedules exceed platform limits. |
| AI risk: AI draft insights could overstate themes, turn sparse reviews into advice, or be affected by prompt injection inside review text. | High | The AI behavior spec requires source links, confidence, draft status, and human approval. Review text must be treated as untrusted evidence. | Decision: maintain verifier plus human gate. Pending implementation tests for prompt builders and unsupported-claim rejection. |
| Data quality: public reviews can be sparse, duplicated, biased, stale, or uneven across platforms and locations. | High | Dashboards and insights must show source coverage, sample counts, date range, confidence, and insufficient-data states. | Pending. Do not present fake precision. Add data quality indicators before claiming client-report reliability. |
| Adoption: importing approved review data and configuring sources may create onboarding friction for small agencies. | Medium | The MVP can begin with CSV import and seeded demo data, but live source setup still needs clear permission notes and status states. | Accepted risk. Future onboarding work should focus on source setup, import validation, and error recovery. |
| Privacy: even public reviews can contain personal information in text, names, or links. Storing author identity must be minimized. | High | The PRD uses hashed author display names and requires compliance-first collection, no private messages, no login-protected content, and server-side secrets only. | Decision: preserve minimization rules. Pending privacy review for review text retention, export content, and source-link display. |
| Demo credibility: a seeded demo can show the logic, but it does not prove live integrations, production performance, or real customer adoption. | Medium | The demo should state it uses seeded or approved demo data and avoid claims about production readiness, customer traction, or live provider coverage. | Decision: use demo as workflow evidence only. Any live integration claim remains pending until implemented and tested. |
| Tenant isolation: cross-agency leakage would be the most serious product failure. | High | The architecture requires `agency_id` filters in every API route, Prisma query, job, report, export, and AI prompt payload. | Decision: keep tenant-scope tests as a release gate. Current Session 18 docs do not modify code or schema. |
| Automation credibility: Zapier can demonstrate workflow concepts, but unmanaged automation could move data outside the controlled tenant and audit model. | Medium | Zapier should remain a course/prototype automation artifact unless reviewed for privacy, tenant scope, audit logging, and approved data movement. | Decision: do not treat Zapier as production architecture without explicit approval. |
